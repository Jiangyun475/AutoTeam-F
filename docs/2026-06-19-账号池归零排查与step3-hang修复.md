## 2. 排查与处置全过程(含弯路)

### 阶段 1 — disabled 把 active 算没了(表层原因)
- `accounts.json` 里其实有 2 个 `status=active` 的号(yun6/yun7,即 Team 两个子席),但都被 `disabled=True`。
- `_display_account_status`(api.py:1251):**任何 disabled 号一律显示成 "disabled"**,无视真实 status;仪表盘 active 计数因此=0。`get_active_accounts`(accounts.py:317)、巡检(api.py:4998)同样过滤 disabled。
- 这些 disabled 的 `disabled_by/disabled_reason/disabled_at` **全是 None**,而所有代码内置禁用路径都会盖元数据 → 判定为**手工直接改 accounts.json** 所致。

### ⚠️ 弯路 1 — 用 JWT exp 误判 token 死活
- 我据 auth 文件里 access token 的 JWT `exp`(还剩 169/201h)断言"yun6/yun7 token 还活着、不需要二次验证",建议重新启用。**这是错的。**
- 重新启用后巡检立刻自动重登,日志铁证:yun6/yun7 **refresh 返回 401**、OAuth **撞 add-phone 手机验证**。
- 教训:**JWT exp 只是 token 内嵌声明,OpenAI 可服务端单方面吊销,exp 没到也照样 401**。判 token 死活要看 refresh 实测 / CPA available / `auth_last_error`,不能信 exp。用户当初的禁用判断是对的。随即恢复禁用止血。

### 阶段 2 — 暂停巡检止损
- 此时所有号 token 失效,巡检每 5 分钟反复重登、撞手机验证墙烧号。
- `_auto_check_config` **无 enabled/pause 开关**,循环是 `_auto_check_stop.wait(interval)`,interval 只有下限无上限。
- 暂停手段:`PUT /api/config/auto-check` 把 `interval` 设超大值(用了 31536000=1 年),PUT 触发 `_auto_check_restart.set()` 立即生效 → 巡检进入超长 wait(日志 `等待 525600 分钟`)。可逆、不重启。

### ⚠️ 弯路 2 — 把 token_invalidated / plan=free 误读成"整批报废"

### 阶段 5 — 定位并修复 step3 hang(根因)
- 位置:`src/autoteam/codex_auth.py` 的 OAuth consent 循环(`for step in range(6)`, ~2754)。
- 机理:`auth_code` 由异步回调捕获;循环在 step3 体内执行到 `_screenshot` 时页面已 redirect/无响应(截图自身 5s 超时能返回),**真正的 hang 在截图之后的 `_is_choose_account_page(page)` 等页面操作**——在无响应页面上做 CDP 调用,**Playwright 的 timeout 对 CDP 级卡死不生效**,于是一直 hang 到 kill 浏览器。而此刻 `auth_code` 早已捕获(OAuth 已完成),根本不该再碰这个死页面。
- 这极可能就是"token 全失效后池子无法自愈"的深层原因之一:每次 reinvite 都卡死 step3、占锁、全堵。"之前快"是因为号 token 没失效、走 refresh 不碰这段完整 OAuth。

**修复**(`codex_auth.py`,consent 循环内、`_screenshot(... step{N}_before ...)` 之后):
```python
            _screenshot(page, f"codex_04_step{step + 1}_before.png")

            # auth code 已捕获 = OAuth 实质完成,此刻页面正在 redirect/可能无响应
            # (screenshot 都超时即页面无响应)。继续在其上做 choose_account/workspace
            # 检测会触发 CDP 级 hang(Playwright timeout 对 CDP 卡死不生效),曾导致
            # reinvite 卡死 ~7 分钟、占住 Playwright 锁堵死整个服务。这里及早 break,
            # 直接去用 auth_code 换 token —— 等价于"kill 浏览器后自然完成"但无需人工。
            if auth_code:
                logger.info("[Codex] auth code 已捕获,跳出 consent 循环 (step %d)", step + 1)
                break
```
break 后流程到达 callback 等待(auth_code 已有立即过)→ `_exchange_auth_code` 换 token(纯 HTTP,不碰死页面)→ 拿 bundle,与"kill 浏览器后自然完成"等价、无需人工。

### 阶段 6 — 重启服务让修复生效(连锁问题)
- 改代码需重启 autoteam(旧代码已 import 内存)。
- ⚠️ 弯路 4:对 tmux pane 发 `C-c` 时,因原 session 是用 `tmux new -d -s ... '直接跑命令'` 起的(pane=命令而非 shell),**C-c 使 pane 退出、`autoteam8787` session 丢失**。已用更健壮方式重建:先 `tmux new-session -d -s autoteam8787`(带 shell),再 `send-keys` 启动命令——以后 C-c 停服务不会再丢 session。
- 启动自检发现 **CPA 也已挂掉**:8317 无响应、`cli-proxy-api` 进程没了、`cpa8317`/`cpa-tunnel` session 消失。CPA `logs/main.log` 最后正常日志 **17:03:47**,bash history 有一条 `tmux kill-session -t cpa8317`(非本次操作所为)。CPA 早停 = 池子本就不工作,重启必需。
- 按系统 bash history 的原命令重启 CPA:
  ```bash
  tmux new -d -s cpa8317 "cd /home/data/jiangyun/2_Auto_team/CLIProxyAPI && ./bin/cli-proxy-api -config ./config.local.yaml"
  ```
  → 8317 返回 200,"API server started successfully",加载 3 个 auth 凭证。
- 再启动 autoteam(新代码):`PYTHONPATH=src .venv/bin/python -m autoteam api --host 0.0.0.0 --port 8787`(cwd=项目根) → 启动完成,**巡检以默认 interval=300(5 分钟)自动开启**(= 打开自动巡检)。

## 5. 经验教训

1. **不要用 JWT exp 判 token 死活**;用 refresh 实测 / CPA available / `auth_last_error`。
2. **`plan=free` / `token_invalidated` ≠ 号废了**;free 是"不在 team"的正常态。唯一真死信号是 OAuth 撞 **add-phone 手机验证**。
3. **验证号是否可用,必须先 invite 进 team 再 OAuth**;只 login 不 invite 永远拿 free。
4. **避免盲目逐个完整 OAuth 探测**——每次撞墙都会加重风控。
5. 重启服务用"shell session + send-keys",别用"pane 直接跑命令"(C-c 会丢 session)。
6. step3 hang 是 CDP 级卡死,Playwright 应用层 timeout 救不了;根治靠"auth code captured 即 break"。
