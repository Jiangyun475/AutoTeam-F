# 僵尸席位(Zombie Seat)问题诊断与优化方案

记录日期: 2026-06-16
分支: `fix/team-rotation-boundaries`
状态: 已诊断,待实现(本文只描述方案,未改动代码)

---

## 1. 现象

- 仪表盘 Team 成员显示 **3 个**,但 active 只有 **1 个**。
- 登录母号(`yun's Workspace`, 账号 `d021352c-…`)实际看到的子号是 **yun11 + yun5**。
- 服务日志稳定复现:
  ```
  [验收] auto-fill 后: team=3/3 active_with_auth=1/2 auth_invalid=1 ...
  [Team] 成员接口存在 8 个隐藏邮箱子号，不能安全确认 yun11 是否已不在 Team；
         未拿到可匹配的 auth JWT  yun11@yunfei.life(auth_invalid)
  [检查] yun11@yunfei.life（已暂停自动修复（手机号验证））
  ```
  > ⚠️ 日志里的"8 个隐藏邮箱子号"**不是说 Team 真有 8 个隐藏子号**(Team 总共才 3 个成员)。
  > 这是 `remove_from_team` 多轮重试查询时 `hidden_member_slots_seen` **跨轮累计**看到的隐藏槽位数。
  > 真实含义是:多轮查询中持续看到隐藏邮箱成员,但始终**无法匹配到 yun11**。

### 三个数字其实是一致的(不是显示 bug)

| 显示 | 真相 |
|---|---|
| 成员 = 3 | 1 母号 + 2 子号(yun5, yun11)。**母号本身也算一个成员**。 |
| active = 1 | 只有 yun5 认证有效、额度可用。 |
| 母号看到 yun11+yun5 | 这就是那 2 个子号,与本地状态吻合。 |

`_count_local_team_seat_accounts` 把状态 ∈ `{active, exhausted, auth_invalid}` 的号都算"占席",
yun11 处于 `auth_invalid` 仍被算席 → 凑成 3/3 满员,但可用席 `active_with_auth=1/2`。

**真正的问题:yun11 是"僵尸席位"——认证已死却赖在 Team 占着 2 个子席中的 1 个,系统又踢不掉。**

---

## 2. 根因:两个机制叠加成死锁

### 机制 A — 身份丢失,认不出隐藏成员
OpenAI 隐藏子号邮箱时,唯一锚点是 JWT 里的 `user_id`。
- `_chatgpt_user_id_for_email()` 只从 **`-team-` 凭证文件** 读 user_id(`_find_team_auth_file` 严格 `codex-{email}-team-*.json`)。
- yun11 的 team 凭证早已丢失:`accounts.json` 里 `auth_file=None`,`auths/` 下只剩
  `codex-yun11@yunfei.life-free-5d3e9595.json`(它自己个人号的 free 凭证)。
- `accounts.json` **从未持久化过 chatgpt user_id**(无该字段)。
- 结果:对账/踢号在隐藏成员里**无法确认哪一个是 yun11** → 跳过,不敢踢。

> 讽刺点:yun11 的 free 文件里其实带着它的 `user_id: user-XKj1LAPmU3L1kgxm5FxmcxfE`(账号级、跨 plan 不变),
> 但当前匹配逻辑刻意不读 free 凭证。

### 机制 B — "等人工修认证"与"占着席位"被绑死
- yun11 重新登录被 OpenAI 卡在 **add-phone(手机号验证)**:
  `auth_last_error=add_phone`,`auth_retry_count=4`,`auth_retry_paused=True`。
- 自动回收路径 `sync_account_states:auth_invalid_recover`(`manager.py:1938`)条件是
  `not in_team and not auth_retry_paused` → yun11 paused 命中"保持 auth_invalid 待人工,不自动回收"。
- 于是它既不被回收为 standby,也不被踢出 Team——连**席位**一起被"留给人工"了。

### 因果链
> yun11 重登被卡 add-phone → 标 `auth_retry_paused`(自动回收主动放弃它)
> → 同时 team 凭证丢失、只剩 free 凭证、又没存过 user_id → 隐藏成员列表里认不出它
> → 对账不敢踢 → 卡死在 Team 占 1/2 子席 → 显示 3/3 满员、实际只有 1 个能用、健康 standby 补不进来。

### 关键证据(只读核查)
- `accounts.json`: yun11 `status=auth_invalid, auth_file=None, auth_retry_paused=True, auth_last_error=add_phone`。
- `auths/`: yun11 仅有 `-free-` 文件,无 `-team-` 文件。
- free 文件 JWT: `chatgpt_account_id=ee9ce792-…`(yun11 个人 workspace,非 team),`user_id=user-XKj1LAPmU3L1kgxm5FxmcxfE`。
- `state_log.jsonl`: 06-15 23:29 起 yun11 进入 auth_invalid 后不再 recover(此前因未 paused 多次 recover)。

---

## 3. 设计总原则

**让死号永远可识别 + 把「需人工修认证」与「占着 Team 席位」彻底解耦。**
能用的 → 留认证、占席位;不能用的 → 踢出释放席位,本地记着"待人工"。

补充安全依据(措辞需严谨,勿写绝对):`auth_invalid` 通常 token 已不可用,**释放其席位的风险显著低于
踢 exhausted/active 号**(后者 token 仍有效,立即踢易触发 `token_revoked` 风控)。但"风险低"不等于"零风险":
仍必须**限于精确匹配确认的不可用占席账号**,并保留**退避(backoff)与审计日志**。不可据此对未精确匹配的成员动手。

---

## 4. 方案(分层)

### Layer 1 — 持久化 `chatgpt_user_id`(身份锚点)
- 新增 accounts.json 字段 `chatgpt_user_id`。
- **持久化时机多打点**(而非仅 active):invite 成功 / reconcile 命中 / sync 命中 user_id 时都写一次,只写一次并校验不变。
- 来源优先级:team auth JWT > `/users` 成员接口 > free/personal JWT。
- **`/users` 作为来源必须加前置条件**:仅当该 member **email 精确匹配本地账号**,或已有可信映射时才能写入。
  隐藏邮箱且未匹配的 member **不得拿来反推绑定**到某账号,否则会把错误的 user_id 写进 accounts.json(误绑风险)。
- 价值:凭证丢失、邮箱隐藏后仍能精确匹配。**注意:只对未来的号有效,救不了已经丢锚点的存量号(如 yun11)。**

### Layer 2 — 隐藏成员匹配优先级(含 free 兜底)
匹配 user_id 的优先级链:
```
email 精确匹配
  → 当前 auth JWT user_id（现有逻辑）
  → accounts.json 历史 chatgpt_user_id（Layer 1）
  → free/personal 凭证 JWT user_id（救存量遗留号）
```
- 新写 `_resolve_member_user_id()` 承载这条链。
- ⚠️ **不要修改 `_find_team_auth_file()`**——它严禁混 plan 是为"当凭证使用"的场景;
  "读 id 认人去踢号"是另一回事,必须分开函数,避免回归(plan 混用会被 OAuth 拒收)。
- 只要 user_id 精确命中,就允许移出 auth_invalid 占席账号。

### Layer 3 — add-phone/paused 死号:释放席位优先 + 隔离
- add-phone 超限后不再反复 OAuth。
- 仍在 Team 且 user_id 可确认 → 直接 kick 释放席位。
- kick 后本地保持 `auth_invalid + auth_retry_paused` —— **这本身就是天然隔离**:
  `get_standby_accounts()` 只选 `standby` 号,`auth_invalid` 根本不会进候选池,无需额外隔离字段。
  - 真正需要隔离字段的是**人工解除后转回 standby 的那一刻**:转 standby 时若不带"待人工已修复"的确认,
    它会立刻被候选池选回 → 再 invite → 再撞 add-phone → 空转浪费 invite 配额、招风控。
  - 因此口径应为:`auth_invalid+paused` 期间天然隔离;人工完成手机验证后才清 `paused`/quarantine 标记并转 standby 放回池。
- 落点:补 `_reconcile_team_members`(1608 行 auth_invalid→KICK 在 Layer 2 修复后自然生效)+
  `sync_account_states` 新增 `in_team and auth_invalid` 主动踢分支。

### Layer 4 — 只读诊断接口(可观测)
新增只读端点,输出:
```
team_occupancy          物理占席数（含母号 / 仅子号两种口径）
active_with_auth         可用席数 / 目标席数
auth_invalid_blockers    占席但认证已死的账号列表（email + 状态 + 失败原因）
hidden_member_count      /users 中隐藏邮箱成员数
unmatched_hidden_members 隐藏成员中无法匹配到本地账号的数量
```
- 让"成员 3 个但 active 1 个"能一键定位是哪个号占席不可用。
- 进阶:`unmatched_hidden_members > 0` 或 `active_with_auth < target` 时**触发告警/补位**,不只是能查。

### Layer 5 — 手动强制清理入口(带保护)
- 后台按钮"移出不可用占席账号"。
- 只允许对 `auth_invalid / exhausted / orphan` 执行。
- 无 email/user_id 精确匹配时,**要求人工确认远端 user_id 或先手动处理,绝不模糊踢人**(误踢最后防线)。

---

## 5. 落地顺序

| 步骤 | 内容 | 风险 | 价值 |
|---|---|---|---|
| 0. 止血(手动) | 从母号移出 yun11,恢复 2 个可用席(执行方式见下) | 低 | 立即回血 |
| 1. 核心改动 | 持久化 `chatgpt_user_id`(L1) + 隐藏成员精确匹配含 free 兜底(L2) | 低-中 | 直接解决当前卡死类型,不降低误踢保护 |
| 2. 策略闭环 | 释放席位优先 + 候选池隔离(L3) | 中 | 防 churn、防复发 |
| 3. 可观测/兜底 | 诊断接口(L4) + 手动清理入口(L5) | 中 | 定位 + 人工兜底 |

> yun11 此刻不 active、未存 id,Layer 1 救不了它 → 必须先走第 0 步手动;
> 这也正是 Layer 2 要加 free JWT 兜底的理由(救其它潜在存量号)。

**第 0 步执行方式(按风险从低到高)**:
1. **最低风险(推荐)**:直接在母号 Web UI 的 Team 成员页,**按邮箱 `yun11@yunfei.life` 手动移除**。
2. 若走 API 删除:**必须先 GET `/users` 确认目标 member 的远端 `user_id` 精确等于 yun11 free JWT 里的
   `user-XKj1LAPmU3L1kgxm5FxmcxfE`**,再 DELETE 该 user_id;严禁凭"隐藏成员里大概是它"模糊删除。

---

## 6. 风险与边界

- **误踢**:只按 user_id 精确匹配,且只针对"本地有记录且判死"的 id;沿用 `remove_from_team` 现有 `already_absent` 多轮重试,避开 OpenAI 同步延迟误判。
- **隔离要有出口**:add-phone 可能临时也可能长期,隔离态必须留人工解除通道,不做永久黑名单。
- **风控**:重申 auth_invalid token 已废,踢它不触发 token_revoked;勿与 exhausted 的"不立即踢"混淆。
- **幂等**:`chatgpt_user_id` 写盘走现有 `update_account`,只写一次、校验不变,避免覆盖。

---

## 7. 测试矩阵(关键用例)

1. in_team + auth_invalid + paused + 邮箱隐藏 + **仅有 free 凭证** → 期望被 kick,本地保留 `auth_invalid+paused`。
2. in_team + auth_invalid + 已持久化 `chatgpt_user_id` + 邮箱隐藏 → 期望按历史 id 命中并 kick。
3. paused 隔离号 → 不被 `get_standby_accounts()` 选回。
4. 健康 active 号 → 任何路径下都不被误踢(精确匹配保护)。
5. 诊断接口 → 在当前 yun11 场景下正确输出 `auth_invalid_blockers=[yun11]`、`active_with_auth=1/2`。
